# Стратегия ветвления: GitHub Flow

## 1. Выбор и обоснование

Для проекта выбрана стратегия **GitHub Flow**. Она рекомендована для небольших команд и хорошо сочетается с принятыми в проекте практиками:

- команда из 2 разработчиков;
- итерации по 1 неделе (Scrumban);
- основная ветка `main` всегда должна быть рабочей и готовой к демонстрации;
- обязательное кросс-ревью и зелёный CI перед слиянием;
- WIP-лимиты: «В работе» ≤ 2, «Ревью» ≤ 2 (см. `process.md`).

## 2. Основная ветка

- **`main`** — единственная долгоживущая ветка.
- `main` всегда должна быть в рабочем состоянии: сборка проходит, линтеры и тесты зелёные.
- Прямой push в `main` **запрещён**. Все изменения попадают только через Pull Request.
- В настройках репозитория включается защита ветки `main`:
  - require pull request before merging;
  - require approvals (минимум 1);
  - require status checks to pass (CI);
  - restrict pushes (только через PR).

## 3. Именование веток

Ветка создаётся от актуальной `main` под конкретную задачу. Используется префикс и ID задачи из бэклога (или краткое описание, если ID нет).

| Тип ветки | Шаблон | Пример |
|---|---|---|
| Новая функциональность (User Story) | `feature/US-XX-краткое-описание` | `feature/US-01-registration` |
| Исправление ошибки | `fix/US-XX-краткое-описание` | `fix/US-04-occupancy-bug` |
| Инфраструктура, CI/CD, рефакторинг | `chore/краткое-описание` | `chore/ci-lint-setup` |
| Документация | `docs/краткое-описание` | `docs/branching-strategy` |

Требования к имени:
- только латиница, цифры и дефис;
- длина — до 50 символов;
- ID задачи (например, `US-05`) обязателен для веток `feature/` и `fix/`, если задача есть в бэклоге.

## 4. Время жизни ветки

- Ветка живёт **от создания до слияния в `main`**.
- Рекомендуемый срок жизни — **не более 1–2 дней**. Это соответствует размеру PR ≤ 300 строк и WIP-лимитам.
- Если задача не помещается в 1–2 дня, её нужно декомпозировать на более мелкие истории / подзадачи.
- После слияния PR ветка **удаляется** (автоматически или вручную). Это снижает визуальный шум и риск случайных пушей в устаревшую ветку.

## 5. Правила слияния

Слияние в `main` выполняется **только через Pull Request (PR)** и при выполнении всех условий:

1. **PR связан с задачей.** В названии или описании PR указан ID задачи (например, `US-05`) и краткое описание.
2. **PR создан из актуальной `main`.** Перед созданием PR автор rebase-ит или merge-ит свежую `main` в свою ветку, чтобы избежать конфликтов.
3. **PR проходит кросс-ревью.** Второй разработчик (не автор) проверяет код. Время на ревью — **в течение 24 часов** с момента создания PR.
4. **CI зелёный.** Все статус-чеки (линтеры, сборка, тесты, если настроены) должны быть успешными.
5. **Размер PR ≤ 300 строк изменений.** Если больше — PR дробится или рефакторинг выносится в отдельную ветку (см. `team-agreement.md`).
6. **Нет блокирующих замечаний.** Все комментарии ревьюера либо исправлены, либо явно закрыты с обоснованием.
7. **Автор не одобряет свой PR.** Требуется одобрение второго участника команды.

**После слияния:**
- ветка удаляется;
- задача перемещается в колонку «Готово» (это часть DoD);
- если CI на `main` неожиданно упал, это блокер: исправление выполняется в приоритетном порядке через отдельный `fix/...` PR.

## 6. Хотфиксы

Для срочных исправлений в `main`:
- создаётся ветка `fix/краткое-описание` (например, `fix/critical-payment-error`);
- PR проходит те же правила: ревью, CI, размер;
- после слияния хотфикс сразу считается готовым к демонстрации / деплою.
