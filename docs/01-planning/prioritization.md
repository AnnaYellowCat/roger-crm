# Приоритизация и состав релиза MVP

---

## 1. WSJF-приоритизация

### 1.1. Шкала и принципы

WSJF (Weighted Shortest Job First) рассчитывается по формуле:

```
WSJF = (BV + TC + RR) / JS
```

Все компоненты оцениваются по шкале Фибоначчи: **1, 2, 3, 5, 8, 13, 21**.

- **BV (Business Value)** — ценность для пользователя и бизнеса.
- **TC (Time Criticality)** — критичность попадания именно в MVP-релиз.
- **RR (Risk Reduction / Opportunity Enablement)** — снижение технических и бизнес-рисков.
- **JS (Job Size)** — размер истории в Story Points (1 SP ≈ 6 часов работы).

Чем выше WSJF — тем раньше история должна попасть в релиз.

### 1.2. Принципы выставления оценок

**BV:**
- **21** — без этого продукт не работает (регистрация, оплата).
- **13** — ключевой сценарий, ради которого приходят пользователи.
- **8** — важная функция, но есть обходной путь.
- **5** — вспомогательная / админская.
- **3** — узкая роль или «приятно иметь».

**TC:**
- **21** — блокирует весь релиз.
- **13** — критично для демонстрации MVP на защите.
- **8** — нужно, но можно добавить в течение итерации.
- **5** — некритично для первой демонстрации.
- **3** — можно отложить без потери смысла MVP.

**RR:**
- **21** — снимает риск потери денег/данных (конкурентность, возвраты).
- **13** — снимает риск некорректных расчётов (формулы, лимиты).
- **8** — снимает эксплуатационный риск (CRUD, статусы).
- **5** — улучшает управляемость (аналитика, цены).
- **3** — косметика/удобство.

**JS:**
- **2** — тривиально (1 форма + 1 CRUD).
- **3** — простая фича.
- **5** — средняя (расчёты + UI).
- **8** — сложная (карта, транзакции).
- **13** — очень сложная (конкурентность, ролевая модель + UI).

**US-01 — Регистрация в системе (WSJF 18.33).**

**US-02 — Пополнение баланса (WSJF 15.67).**

**US-05 — Расчёт стоимости брони (WSJF 9.40).**

**US-07 — Защита от двойного бронирования (WSJF 3.62).**
BV = 13: пользователь ожидает, что место не «уведут». TC = 13. RR = 21: **критично** — двойное бронирование = возвраты и потеря репутации. JS = 13: транзакции БД + блокировки + обработка гонок. Низкий WSJF из-за высокого JS.

**US-08 — Оплата брони с баланса (WSJF 11.00).**
BV = 21: ядро e-commerce. TC = 21: без оплаты проект не имеет смысла. RR = 13: списание должно быть атомарным. JS = 5: транзакция + проверка баланса + запись в `transactions`.

**US-09 — Отмена брони с возвратом (WSJF 7.80).**
BV = 13: пользователь должен уметь вернуть деньги при изменении планов. TC = 13. RR = 13: правила 24 часа и корректный возврат. JS = 5: проверка срока + возврат на баланс + новая транзакция.

**US-10 — Управление пользователями (WSJF 4.25).**
BV = 13: admin должен управлять ролями. TC = 13: нужно для демо админки. RR = 8: защита от удаления себя. JS = 8: таблица + CRUD + смена ролей.

**US-11 — CRUD построек (WSJF 4.88).**
BV = 13: без этого admin не может поддерживать состав. TC = 13. RR = 13: soft delete сохраняет историю броней. JS = 8: форма с координатами на карте + валидация.

**US-12 — Вывод из строя + компенсация (WSJF 5.80).**

**US-13 — Создание акции/промокода (WSJF 4.20).**

## 2. Ёмкость команды на MVP

### 2.1. Параметры

- **Длительность MVP:** 4 недели (1 итерация).
- **Состав команды:**
  - 2 разработчика (fullstack) × 20 ч/нед = 40 ч/нед
  - **Итого:** 40 ч/нед.
- **Коэффициент фокуса:** 0.9 (команда из 2 человек, знакомая со стеком; потери на ревью и коммуникацию минимальны).

### 2.2. Расчёт часов

```
Доступно часов = 4 нед × 40 ч/нед × 0.9 = 144 ч
```

### 2.3. Пересчёт в Story Points

Для студенческого проекта принимаем **1 SP ≈ 6 часов** (консервативно: часть времени уходит на изучение стека, отладку, ревью).

```
Ёмкость MVP = 144 ч / 6 ч/SP = 24 SP
```

### 2.4. Проверка на здравость

Сумма SP всего бэклога:

```
3 + 3 + 8 + 8 + 5 + 5 + 13 + 5 + 5 + 8 + 8 + 5 + 5 + 8 + 3 = 92 SP
```

В MVP войдёт ~26 % бэклога — реалистично для 4-недельной итерации команды 2 FTE.

**Итого ёмкость MVP: `W = 24 SP`.**

## 3. Модель задачи о рюкзаке

### 3.1. Переменные

`x_i ∈ {0, 1}` — история `i` включена в MVP (1) или нет (0).

### 3.2. Целевая функция

Максимизируем суммарную ценность релиза по WSJF:

```
max  Σ v_i · x_i
```

где `v_i` — WSJF-скор истории `i`.

### 3.3. Ограничение ёмкости

```
Σ w_i · x_i ≤ W = 24
```

где `w_i` — Story Points истории `i`.

### 3.4. Ограничения зависимостей

Если история `j` зависит от `i`, то:

```
x_j ≤ x_i     ∀ (j → i)
```

| История | Зависит от | Обоснование |
|---|---|---|
| US-02 | US-01 | Нужен аккаунт |
| US-03 | US-01 | Нужен аккаунт |
| US-04 | US-03 | Занятость — в карточке постройки на карте |
| US-05 | US-03 | Расчёт — из карточки постройки |
| US-06 | US-05; US-13 | Промокод применяется к рассчитанной сумме; код создаётся менеджером |
| US-07 | US-05 | Нужна логика создания брони |
| US-08 | US-02; US-05 | Нужен баланс и рассчитанная бронь |
| US-09 | US-08 | Отменять можно только оплаченную |
| US-10 | US-01 | Нужны пользователи в системе |
| US-11 | US-03 | Постройки отображаются на карте |
| US-12 | US-11; US-08 | Нужна сущность постройки и оплаченные брони |
| US-13 | US-01 | Роль manager должна существовать |
| US-14 | US-08 | Аналитика по оплаченным броням |
| US-15 | US-11 | Цены — часть постройки |

### 3.5. Обязательные истории

```
x_US-01 = 1   (регистрация — без неё нет пользователей)
x_US-08 = 1   (оплата — без неё нет e-commerce)
```

### 3.6. Итоговая модель

```
max  Σ v_i · x_i
s.t. Σ w_i · x_i ≤ 24
     x_j ≤ x_i,   если j зависит от i
     x_US-01 = 1, x_US-08 = 1
     x_i ∈ {0, 1}
```

### 3.7. Граф зависимостей

```
US-01 ── US-02 ─┐
   │           ├── US-08 ── US-09
   │           │       ├── US-12
   │           │       └── US-14
   │           └── US-05 ── US-06 ── US-13
   │                   └── US-07
   ├── US-03 ── US-04
   │        ├── US-05
   │        └── US-11 ── US-12
   │                └── US-15
   ├── US-10
   └── US-13
```

### 4.5. Объяснение расхождений

Жадное и оптимальное решения **совпали** — и это ожидаемый результат для данной конфигурации бэклога. Причины:

1. **Must-замыкание занимает всю ёмкость.** Обязательные истории `US-01` (3 SP) и `US-08` (5 SP) вместе с их транзитивными зависимостями `US-02` (3 SP, нужна для баланса при оплате), `US-05` (5 SP, нужна рассчитанная сумма), `US-03` (8 SP, карточка постройки для расчёта) в сумме дают ровно **24 SP = W**. Свободной ёмкости не остаётся, поэтому ни одна необязательная история не может быть добавлена — ни жадно, ни оптимально.

2. **Жадный алгоритм стартует с must-замыкания.** По логике `release_planner.py` жадно сначала фиксирует все must-истории и их зависимости (`forced`), затем сортирует остальные по `v/w` и пытается добавить, если помещается. Поскольку после фиксации must занято уже 24 SP, цикл «добора» не добавляет ничего. Оптимум (ветви и границы) приходит к тому же множеству — все альтернативы либо не проходят по ёмкости, либо нарушают зависимости.

3. **Зависимости «съедают» ценность.** Рассмотрим альтернативу: отказ от `US-03` (8 SP, WSJF 4.25) освободил бы ёмкость под `US-09` (5 SP, WSJF 7.80) + `US-04` (8 SP) — но `US-04` зависит от `US-03`, а `US-05` зависит от `US-03`. Без карты нельзя ни рассчитать бронь, ни показать занятость. Транзитивное замыкание `US-03` жёстко входит в must-цепочку — замены нет.

4. **Граница «дробного рюкзака» в ветвях и границах даёт верхнюю оценку.** При W=24 и must-замыкании на всю ёмкость верхняя граница равна 58.65 (ценности must-замыкания). Поскольку уже на корне дерева `bound` совпадает с достижимым значением, ветвление быстро отсекается — отсюда всего 11 узлов.

5. **Когда жадный мог бы проиграть?** Если бы ёмкость была больше (например, `W = 30`), жадный мог бы «застрять» на `US-09` (7.80 / 5 SP = 1.56), тогда как оптимум предпочёл бы `US-12` (5.80 / 5 SP = 1.16, но с зависимостью `US-11` = 8 SP) — здесь уже нужен перебор. При `W = 24` такой развилки нет.

**Вывод:** при выбранной ёмкости `W = 24 SP` must-замыкание полностью определяет состав MVP, и жадный алгоритм не может ошибиться. Это **не** означает, что жадный всегда оптимален — на других ёмкостях (например, 30–40 SP) расхождение проявится, и метод ветвей и границ даст лучший результат.

## 5. Состав MVP (итоговый)

### 5.1. Важное различие: MoSCoW-приоритет ≠ состав MVP

В проекте используются **две разные шкалы приоритета**, и их не нужно смешивать:

| Шкала | Где применяется | Что означает |
|---|---|---|
| **MoSCoW** (Must / Should / Could) | User Story Map (draw.io) | Приоритет истории **вообще**, вне зависимости от ёмкости релиза |
| **WSJF + задача о рюкзаке** | `prioritization.md` | Какие истории **физически помещаются** в MVP при `W = 24 SP` |

**Следствие:** на карте историй приоритет **Must** имеют 9 историй — это «список необходимого». Но в **состав MVP** попадают только 5 — те, что максимизируют WSJF при ограничении ёмкости и зависимостей. Остальные Must-истории — **первые кандидаты на релиз 1.1**, как только расширится ёмкость команды.

Это **не противоречие**: Must отвечает на вопрос «насколько история важна вообще», а MVP — на вопрос «что влезает в 24 SP с учётом зависимостей». Оба ответа правильные, просто на разные вопросы.

### 5.2. Состав MVP (по результатам задачи о рюкзаке)

| ID | История | SP | WSJF | Роль | MoSCoW |
|---|---|---|---|---|---|
| US-01 | Регистрация в системе | 3 | 18.33 | customer | Must |
| US-02 | Пополнение баланса | 3 | 15.67 | customer | Must |
| US-03 | Просмотр карты, выбор постройки и оформление брони | 8 | 4.25 | customer | Must |
| US-05 | Расчёт стоимости брони | 5 | 9.40 | customer | Must |
| US-08 | Оплата брони с баланса | 5 | 11.00 | customer | Must |
| **Итого** | | **24** | **58.65** | | |

**Что вошло и почему:**

Планируемый MVP **должен покрыть** сквозной e-commerce-сценарий покупателя: регистрация → пополнение баланса → просмотр карты → оформление брони → расчёт стоимости → оплата. Это минимальный цикл, при котором продукт имеет смысл: пользователь может зарегистрироваться, найти объект, заполнить форму брони, узнать цену и оплатить бронь с внутреннего баланса. Цепочка зависимостей `US-01 → US-02 → US-08 → US-05 → US-03` жёстко связывает эти пять историй — убрать любую нельзя без разрушения сценария.

### 5.2.1. Детализация US-03 (форма брони)

US-03 включает не только просмотр карты и карточку постройки, но и **форму оформления брони** — без неё кнопка «Забронировать» никуда не ведёт. Форма входит в те же **8 SP** (оценка не меняется — форма «внутри» сценария «увидел → выбрал → оформил»).

- **AC-3.4 (форма открывается).** **Дано** я на карточке постройки и нажимаю «Забронировать», **когда** форма открывается, **тогда** я вижу поля, зависящие от типа постройки:
  - **коттедж:** дата заезда, дата выезда, число мест (все места коттеджа — целиком);
  - **беседка:** дата, время начала (8:00–23:00), время окончания (8:00–23:00), число мест (все места — целиком);
  - **бассейн:** дата, время начала (8:00–23:00), время окончания, выбор **отдельных мест** (чекбоксы).

- **AC-3.5 (валидация формы).** **Дано** я заполнил форму брони, **когда** нажимаю «Рассчитать», **тогда** форма проверяет:
  - даты в будущем (не в прошлом);
  - для беседки/бассейна — время в диапазоне 8:00–23:00 (иначе ошибка «Доступное время: 8:00–23:00»);
  - для коттеджа — дата выезда > дата заезда;
  - выбранные места/часы не заняты (проверка через бэкенд);
  - для коттеджа/беседки — выбраны все места (нельзя снять «3 из 5»);
  - при ошибке — сообщение под полем, кнопка «Рассчитать» не отправляет запрос.

- **AC-3.6 (передача в расчёт).** **Дано** форма валидна, **когда** я нажимаю «Рассчитать», **тогда** данные формы передаются в US-05 (расчёт стоимости), и я вижу итоговую сумму и кнопку «Оплатить».

**Что отложено, несмотря на MoSCoW Must:**

- **US-04 (просмотр занятости)** — Must по важности, но в рюкзак не помещается: зависит от US-03, а вместе с US-03/US-05/US-08 превышает `W = 24 SP`. Релиз 1.1.
- **US-07 (защита от двойного бронирования, JS=13)** — Must по риску (RR=21), но 13 SP съедают больше половины ёмкости. Релиз 1.1 вместе с оптимистичными блокировками БД.
- **US-09 (отмена с возвратом, WSJF=7.80)** — Must по бизнес-логике, но не помещается при `W = 24`. Релиз 1.1.
- **US-10 (управление пользователями)**, **US-11 (CRUD построек)**, **US-13 (акции)** — Must для соответствующих ролей (admin / manager), но в customer-сценарий MVP не входят. Релиз 1.1 (admin/manager-релиз).
- **US-06, US-12, US-15** — Should по MoSCoW, отложены в релиз 1.1–1.2.
- **US-14 (аналитика, WSJF=1.63)** — самая низкая ценность, страница **не реализована**, есть только описание в ТЗ. Релиз 1.2+.

### 5.3. Соответствие карте историй

На User Story Map (draw.io) красные линии MVP отделяют истории, **вошедшие в релиз** (5 историй, перечисленных в п. 5.2), от отложенных. Истории US-04, US-07, US-09, US-10, US-11, US-13 остаются на карте с приоритетом **Must** (это их MoSCoW-статус), но **не входят в MVP** по результатам задачи о рюкзаке — они первые кандидаты на релиз 1.1.
