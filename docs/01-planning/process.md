# Организация процесса разработки

## 1. Выбор методологии: Scrumban

Для проекта CRM-системы выбрана гибридная методология **Scrumban**, объединяющая структуру Scrum и гибкость Kanban.

### Обоснование выбора по ключевым факторам

| Фактор | Scrum | Kanban | Scrumban (выбор) |
| :--- | :--- | :--- | :--- |
| **Размер команды** | Требует чётких ролей (SM, PO, Dev Team) | Не регламентирует роли | Для команды из 2 человек избыточные роли Scrum не нужны, но нужна структура итераций |
| **Стабильность требований** | Подходит для стабильных требований с редкими изменениями | Подходит для потока задач с частыми изменениями приоритетов | Требования в учебном проекте могут уточняться после фидбэка преподавателя, но ядро (MVP) зафиксировано |
| **Частота обратной связи** | Спринты (1–4 недели) | Непрерывный поток | Нужны регулярные контрольные точки (демо преподавателю), но без жёстких церемоний |
| **Управление загрузкой** | Через планирование спринта | Через WIP-лимиты | Комбинация: планирование итераций + WIP-лимиты для предотвращения перегрузки |
| **Документация** | Обязательные артефакты (бэклог, инкремент) | Минимальная | Достаточно бэклога, DoR/DoD и карты историй |

**Вывод:** Scrumban позволяет работать короткими итерациями (по 1–2 недели), но при этом использовать WIP-лимиты для защиты команды от перегрузки и сохранять гибкость при изменении приоритетов внутри итерации.

## 2. Настройка доски задач

### Колонки доски и WIP-лимиты

| Колонка | WIP-лимит | Обоснование (Закон Литтла) |
| :--- | :---: | :--- |
| **Бэклог (Backlog)** | — | Неограниченно: здесь хранятся все задачи проекта |
| **Готово к работе (Ready)** | — | Неограниченно: задачи прошли DoR, но ещё не взяты в работу |
| **В работе (In Progress)** | **2** | Команда из 2 человек. Каждый разработчик ведёт одну задачу. Закон Литтла: `L = λ × W`. При пропускной способности λ ≈ 2 задачи/неделю и среднем времени выполнения W ≈ 1 неделя, среднее число задач в работе L = 2. Превышение лимита ведёт к многозадачности и росту W (времени цикла) |
| **Ревью (Review)** | **2** | Ревью выполняет второй разработчик (кросс-ревью). Лимит 2 позволяет не создавать очередь на ревью, но и не отвлекать обоих одновременно. Закон Литтла: если λ_ревью ≈ 2 задачи/неделю, W_ревью ≈ 0.5 недели, то L_ревью = 1. Лимит 2 даёт запас на случай всплеска |
| **Готово (Done)** | — | Неограниченно: задачи, прошедшие DoD |

**Закон Литтла** гласит: `L = λ × W`, где `L` — среднее количество задач в системе (в колонке), `λ` — средняя пропускная способность (задач в единицу времени), `W` — среднее время нахождения задачи в системе. WIP-лимит напрямую ограничивает `L`, что заставляет команду либо увеличивать `λ` (работать эффективнее), либо уменьшать `W` (дробить задачи, ускорять ревью).

## 3. Definition of Ready (DoR)

Задача считается готовой к взятию в работу, если выполнены **все** условия:

1.  **Сформулирована как User Story** по шаблону «Как…, я хочу…, чтобы…».
2.  **Имеет минимум 2 критерия приёмки** в формате Дано / Когда / Тогда.
3.  **Оценена в Story Points** (Planning Poker).
4.  **Имеет приоритет** (Must / Should / Could) и входит в текущую итерацию или MVP.
5.  **Не имеет блокирующих зависимостей** от незавершённых задач (или зависимости явно указаны и не мешают началу работы).
6.  **Понятна исполнителю**: нет открытых вопросов по бизнес-логике, UI или технической реализации.

---

## 4. Definition of Done (DoD)

Задача считается завершённой, если выполнены **все** условия:

1.  **Код написан** и соответствует требованиям из критериев приёмки.
2.  **Пройдено код-ревью** вторым разработчиком (Pull Request одобрен).
3.  **Pull Request связан с задачей** (в названии или описании PR указан ID задачи, например `US-05`).
4.  **Функционал проверен вручную** на соответствие критериям приёмки (тестирование выполнено одним из разработчиков).
5.  **Код слит в основную ветку** (`main` / `dev`) через Pull Request (не напрямую).
6.  **CI-конвейер прошёл успешно** (сборка, линтеры, тесты — если настроены).
7.  **Задача перемещена в колонку «Готово»** на доске задач в момент фактического завершения.
8.  **Обновлена документация** (если требуется: описание API, схема БД, README).

## 5. Работа с трекером и репозиторием

### Выбранный инструмент: **Kaiten**

**Почему Kaiten:**
- Бесплатный тариф доступен бессрочно для команд до 5 человек (до 3 пространств и 5 досок) — этого с запасом хватит для команды из двух человек.
- Встроенные дополнения для GitHub и GitLab: коммиты, ветки и пулл-реквесты автоматически связываются с карточками задач.
- Гибкая настройка колонок и WIP-лимитов (ограничений НЗП) для контроля загрузки команды.
- Полностью доступен в России без VPN, интерфейс и поддержка на русском языке.
